## 0. 为什么有这一期（一句话）

用户试玩导出的「雾渡」后说得对：**这不能叫游戏**。7 个场景、每段正文都是同一句「你来到 X。气氛紧绷，每个选择都有代价。」、一个 `trust` 变量、三下结局。P0 → M1b 做的全是管线（引擎、存档、发布、导出 HTML/exe），管线已通，**exe 打包用户已真机确认，关闭**；但「从想法或小说产出一个真游戏」这条流程从来没有被当成产品做过。

本期把重心放到 **游戏产出流程**：
1. 先用一份策划手写的 **修仙金样本《寿灯》** 定义「什么叫游戏」，它是流程必须能产出的**标尺**（§2–§4）；
2. 审计今天的产出流程为什么只能产出模板句游戏（§5）；
3. 设计目标流程：输入 → 世界设定集 → 结构 → 内容生成 → lint → 作者审改 → 模拟试玩报告 → 发布 → 导出（§6），**作者侧接真模型**纳入设计（§7）；
4. 拆成 3 个可实现切片 S1/S2/S3，每片验收都对照金样本，且**每片都要回归 HTML + exe 导出**（§8、§9）。

## 1. 及格线（「这算一个游戏」的可验收标准）

每条都是一个数字门槛，由 lint v2（§6.6）或模拟器（§6.7，5 种策略 × 200 种子）自动判定；只有 G1 的人工计时与 G10 的离线试玩要人做。**金样本必须全部达标；S2 / S3 生成局按 §8 的比例达标。**

| # | 维度 | 及格线 | 判定 |
|---|---|---|---|
| G1 | 时长 | 首通 ≥ 60 次决策，且读到 ≥ 10,000 字不重复正文（≈ 30 分钟）；人工首通 ≥ 30 分钟 | 模拟器 `random` 中位数 + 人工计时 1 次 |
| G2 | 结局 | ≥ 4 个普通结局 + ≥ 2 个失败结局 + 1 个时限结局；每个结局至少被 1 种策略以 ≥ 5% 打到；`random` 下任一结局 ≤ 60%；结局正文两两相似度 < 0.5 | 模拟器 + lint |
| G3 | 资源 | ≥ 4 种资源，全部有 `min/max`；每种 ≥ 3 处门控（≥ / ≤ / 区间）；≥ 2 种在触底或封顶时有后果（结局或强制卡） | lint |
| G4 | 卡池 | ≥ 40 张卡，其中 ≥ 15 张可重复；每张可重复卡 ≥ 2 段变体；连续两回合抽到同一张 = 0 次 | lint + 模拟器 |
| G5 | 随机可复现 | 抽卡与掷骰都用存档里的种子；同种子 + 同操作序列 ⇒ 结果逐字相同 | 引擎单测 + 存档重放 |
| G6 | 时钟 | 可见年月 + 寿元倒计时；≥ 2 个限时窗口；时限结局在「偷懒」策略下可达 | lint + 模拟器 |
| G7 | 正文 | 禁用句 0 命中；剧情卡每段 ≥ 120 字，地点 ≥ 150 字；非变体正文两两相似度 < 0.6 | lint |
| G8 | 取舍 | 开局 ≥ 3 个去向不同的行动；≥ 70% 的选项改动至少 1 个资源或事实；每回合可见选项里 ≥ 1 个有代价 | lint + 模拟器 |
| G9 | 诚实 | 卡住的选项可见不可点并给原因，格式「灵石不足：需 ≥ 30，现有 12」；没有「能点但报错」 | 投影单测 + UI 截图 |
| G10 | 交付 | 同一份内容导出 HTML 单文件和 Windows exe，都能断网从开局玩到结局 | §9 打包回归 |

> G1 的代理指标理由：按 400 字/分钟阅读 + 每次决策 5–10 秒思考，60 次决策 + 1 万字 ≈ 30–35 分钟。

## 2. 金样本世界：《寿灯》

### 2.1 一句话、基调

- **一句话**：青崖宗祠堂里每个弟子都有一盏魂灯，你的灯油只剩四十年——有人借走了你的寿。你要在灯灭之前，决定是修上去、查下去、借回来，还是回家去。
- **基调**：克制、冷、带人情味的凡人修仙。不写爽文打脸；写时间、穷、代价和选择。文风参照「短句 + 具体物件 + 不解释情绪」，每段至少一个具体可感的细节（灯芯、霉味、铜钱、雨）。
- **玩家身份**：外门杂役弟子，十六岁，三灵根，起始炼气一层。

### 2.5 核心循环

```text
每一轮（≈ 1–36 个月）：
  看 HUD（修为 / 寿元 / 灵石 / 心魔 / 时钟）
    → 在当前地点：固定行动（修炼 / 打工 / 移动）+ 手牌里的 3 张剧情卡
    → 选一个：花时间、花灵石、冒心魔风险，换修为 / 灵石 / 线索 / 好感
    → 时钟走：寿元按年扣；限时事件开关；手牌刷新
    → 修为封顶 → 「瓶颈」卡 → 突破（种子随机判成败）
    → 资源触底 / 封顶 → 失败或强制剧情；满足结局条件 → 结局
```

四股力量互相拉扯（**这就是游戏性**）：
- **时间 vs 修为**：闭关最快涨修为，但寿元一直在扣；
- **灵石 vs 安全**：黑市筑基丹便宜一半，但心魔 +15；
- **心魔 vs 捷径**：强冲关、借寿、杀人夺宝都快，但心魔封顶就走火入魔；
- **真相 vs 自保**：查借寿要花大量时间，还会得罪长老（功勋清零风险）。

### 2.6 境界进度（预期节奏）

| 境界 | 典型游戏内年份 | 突破成功率（基础） | 寿元上限 |
|---|---|---|---|
| 炼气前 → 中 | 第 2–4 年 | 70% | 40 |
| 炼气中 → 后 | 第 6–9 年 | 55% | 40 |
| 炼气后 → 筑基 | 第 12–20 年 | 25%（+筑基丹 35%） | 120 |
| 筑基 → 结丹 | 第 30–45 年 | 15%（+秘境「结丹灵物」 30%） | 300 |

成功率公式：`基础 + 丹药加成 − 心魔 × 0.5%`，夹在 5% – 95%。基础率按境界分档，用 `chance.mods` 的 `atMost` / `atLeast` 表达（D5）。失败：修为 −40、心魔 +10、寿元 −1。「典型年份」是设计目标，第一批模拟显示冲刺打法结丹偏快（见 §4.3），由第二、三批调平。

## 3. 引擎现状 vs 必须新增（系统增量）

### 3.1 今天引擎实际支持什么（读 `packages/contracts` + `packages/play-runtime` 得出）

| 能力 | 故事模式 `story`（`GameContent`） | 开放模式 `open`（`WorldContent`） |
|---|---|---|
| 内容单位 | 场景 ≤ 100、每场景选项 ≤ 8；**纯有向图，每个场景读一次** | 地点 3–40、行动 3–80、事件 ≤ 40、结局 1–12 |
| 条件 | `variable.equals`、`variable.gte`（**无 ≤、无区间**） | `fact` / `known` / `npc_knows` / `time.atLeast` / 地形·势力·区域 / `faction_relation(atLeast, atMost)` / `npc_at_location` / **`resource.atLeast`（无 atMost）** |
| 效果 | `variable.set`、`variable.increment` | `set` / `reveal` / `npc_learn` / `move` / `npc_move` / **`resource.delta`** / 领地 / 势力关系 / `start_encounter` 桩 |
| 上下限 | **无**；只有世界书 `cap_variable_increment`（限单次增量，不限总量）、`require_min/max_variable`（按 tag 卡选项） | 同左；资源可以无限涨、可以变负数 |
| 触底 / 封顶后果 | 无 | 无；只能靠 `events.when` 绕（但 `resource` 条件只有 ≥） |
| 可重复内容 | **不可能**（图上每个场景只走一次） | 行动 `once:false` 可重复，但**文案永远一样**；事件**每个只触发一次** |
| 随机 | **无** | **无**（P2 掉落是确定性桩） |
| 时钟 | 无 | `elapsed` + `timeLimit`（**3–100**）+ 行动 `timeCost`（**1–5**）；到点给 `timeoutEnding`；没有年 / 月显示，没有周期规则 |
| 锁定选项显示 | **直接隐藏**（`projectSession` 过滤掉） | 可见 + `enabled:false` + `blockedReason`（✔ 诚实） |
| 存档 | `SessionState`；`RUNTIME_VERSION` 不同 ⇒ 诚实标「旧版本」，不迁移 | `AdventureState schemaVersion:1`；同左 |

**结论：**
1. 故事模式的图结构天生撑不起 30 分钟 + 可重复卡；**金样本放在开放模式**（地点 + 行动 + 时间 + 资源都已有，最接近 80 Days / Fallen London 的形状）。
2. 开放模式缺的是：资源的 min/max 与触底触发、≤ 与区间条件、剧情卡池 + 手牌、种子随机、成败判定、长时钟与周期规则、文案变体。
3. 故事模式本期**不动**（只在 Out 里登记 `variable.lte` 与「锁定可见」以后补）。

规则（引擎）：

- 当前上限可变：新效果 `resource_max`（见 d），存进存档 `resourceMax`。
- 世界书 `cap_variable_increment` 照旧先作用（单次增量），再夹紧。

#### (c) 剧情卡池 `storylets` + 手牌

```jsonc
"storyletRules": { "handSize": 3, "refreshOn": ["move", "clock"], "refreshEveryMonths": 3 },
"storylets": [
  {
    "id": "chaojing", "title": "替人抄经",
    "locationIds": ["fangshi"],                  // 省略 = 任意地点
    "when": [{ "kind": "resource", "resourceId": "lingshi", "atMost": 199 }],
    "weight": { "base": 10, "mods": [{ "when": [{ "kind": "resource", "resourceId": "lingshi", "atMost": 20 }], "add": 15 }] },
    "repeat": { "cooldownTurns": 4, "maxTimes": 8 },   // 不写 = 一次性（once）
    "urgent": false,                              // true = 条件一满足就强制进手牌（瓶颈 / 限时事件）
    "textVariants": ["……变体一……", "……变体二……"],   // 一次性卡可只写 "text"
    "variantMode": "random",                      // random：种子随机、同一段不连用；sequential：按打出次数取
    "choices": [
      {
        "id": "write", "label": "接下这单（三个月）", "timeCost": 3,      // 0 = 不走时间
        "availableWhen": [],                       // 不满足 = 隐藏（如按境界分档的冲关选项）
        "requires": [],                            // 不满足 = 灰掉 + 原因
        "effects": [{ "kind": "resource", "resourceId": "lingshi", "delta": 18 }],
        "text": "……结果文案……"
      }
    ]
  }
]
```

规则（引擎）：
- **候选**：地点匹配 ∧ `when` 全满足 ∧ 不在冷却 ∧ 未到 `maxTimes` ∧（一次性卡）未用过 ∧ 不在当前手牌。
- **抽牌**：`urgent` 卡先入手；其余按权重用种子随机**无放回**抽到 `handSize`。手牌存进存档，读档后不变。
- **刷新**：移动、或时钟走过 `refreshEveryMonths` 时刷新未使用的牌；打出的牌进入冷却。
- **投影**：手牌里的卡显示 `title` + 正文 + 选项；选项不满足 `requires` 时**可见不可点**并带原因（与开放行动一致）。
- 剧情卡选项 = 一次「行动」：走同一套 `timeCost` / `effects` / 世界书 spend / `settle()`。

- 「同种子 + 同操作序列 ⇒ 结果逐字相同」写成单测（G5）。

#### (e) 时钟 `clock`

```jsonc
"clock": {
  "unit": "month", "startYear": 1, "startMonth": 3,
  "display": "第{year}年 {month}月",
  "limitMonths": 720,                          // 取代 timeLimit 的上限（timeLimit 仍保留给旧内容）
  "timeoutEndingId": "liushi",                 // 到点结局（kind: timeout）
  "countdownResourceId": "shouyuan",           // HUD 倒计时用哪个资源（C4）；不写时 UI 按 §3.5 推断
  "rules": [
    { "everyMonths": 12, "effects": [{ "kind": "resource", "resourceId": "shouyuan", "delta": -1 }] }
  ],
  "windows": [                                 // 限时事件窗口：开、关时各推一次 urgent 卡
    { "id": "xiaobi_1", "fromMonth": 30, "toMonth": 33, "storyletId": "xiaobi", "label": "外门小比" },   // 第 3 年 9–12 月
    { "id": "luoxing_1", "fromMonth": 96, "toMonth": 119, "storyletId": "luoxing_open", "label": "落星秘境" },
    { "id": "dabi_1", "fromMonth": 120, "toMonth": 123, "storyletId": "dabi", "label": "宗门大比" }  // 第 11 年 3–6 月
  ]
}
```

- **月序号 = 已过月数（D2）**：开局 = 第 0 月；显示年月 = `startYear / startMonth + month` 推出；窗口、条件、`limitMonths` 都用已过月数。UI 只显示投影给的日历文字与 `monthsLeft`，不自己换算。
- 契约放宽：有 `clock` 时 `timeCost` 放宽到 **0–120**（0 只用于剧情卡选项）、`limitMonths` ≤ 2400；没有 `clock` 时校验与今天完全一样。
- 一次行动跨过多个 `everyMonths` 边界时，规则按次数逐次结算（闭关 36 个月 = 寿元 −3）。

## 5. 审计：今天的产出流程为什么只能产出「模板句游戏」

### 5.1 今天的流程（读代码得出）

```text
作者：导入小说 txt（sources）→ 选章节 + 玩家身份 + 方向 + 粒度 + 数值模板（GenerationPanel「改编桌」）
  → 生成任务（generation/runner.ts，worker 进程）
     1. analyze：按 12,000 字切块，每块一次模型调用 → 人物 / 地点 / 世界规则 + 证据
     2. merge：拼接（不做别名合并）
     故事模式：
     3. generate_skeleton：一次调用产出整张图（3–16 个场景，正文「可留空或极短占位」）
     4. expand_scenes：一次调用把**整张图所有场景**的正文一起写完
     开放模式：
     3. generate_world：一次调用产出整个 WorldContent
     每步：zod 校验 → 失败则带错误回喂重试（repair ≤ 3）；网络错误退避重试
  → 草稿（Draft / WorldDraft）
  → 作者编辑：画布改图、场景编辑器、变量与选项规则、世界书；单场景「补全文」(fill-scene-text)；单点「向外生长 1–2 个场景」(extend-scenes)
  → 发布门禁（rules/playability.ts：开局密度、走廊、假分支、结局数、结局正文相似度、效果占比……）
  → 发布 GameRevision / WorldRevision → 工作台试玩 / 玩家壳 /play → 导出 HTML / exe
```

模型接入：`ChatCompletionsProvider`（OpenAI 兼容 Chat Completions，JSON 输出，zod 校验 + 修复回喂 + 退避），配置走 `.env` 或网页「模型设置」。测试与 e2e 走 `/workspace/btg-e2e/mock-llm.mjs`（本机 4399 端口的假模型）。

### 5.2 根因（按影响排序）

| # | 根因 | 证据 | 后果 |
|---|---|---|---|
| R1 | **交给用户的雾渡是假模型产出的** | `mock-llm.mjs` 第 334 行：骨架正文为空时一律填 `你来到「${scene.title}」。气氛紧绷，每个选择都有代价。`；e2e 与导出样例都由它生成 | 用户看到的「游戏」只是管线测试夹具 |
| R2 | **发布门禁不看正文** | `playability.ts` 只查图结构和结局文案；场景正文没有最短长度、模板句、重复度检查 | 万能句也能通过门禁、发布、导出 |

| R9 | **验收只盯管线** | P0–M1b 每期验收清单都是管线项 | 策划责任：本期起每片验收都含「内容及格线」 |

## 6. 目标流程（端到端）

```text
 ①输入 ──► ②世界设定集 ──► ③结构计划 ──► ④内容生成 ──► ⑤组装 ──► ⑥lint ──► ⑦模拟试玩报告
 想法/小说    (AI 起草·作者锁定)  (AI 起草·规则检查·作者锁定)  (AI 逐卡·规则校验)  (规则)   (规则)    (规则)
                                                                       │
                     ◄──────── ⑧作者审改回路（单卡重生成 / 锁定 / 手改；增量 lint+模拟）◄──┘
                                                                       │
                                                         ⑨发布（门禁）──► ⑩导出 HTML / exe（已有）
```

每一步都产出**落库的中间产物**（可恢复、可重跑、可人审），沿用 runner 的检查点与修复回喂机制。

### 6.1 ① 输入

| 项 | 内容 |
|---|---|
| 输入 | **想法**：表单（题材 / 主角是谁 / 他想要什么 / 什么在阻止他 / 基调 / 篇幅档位 S·M·L），≤ 2,000 字；**或小说**：已有 sources + 选章（沿用） |
| 输出 | `ProductionBrief { kind:'idea'|'novel', genre, protagonist, desire, obstacle, tone, length:'S'|'M'|'L', sourceId?, chapterIds?, analysisId? }` |
| 谁做 | 作者填；小说路径额外跑现有 analyze/merge（AI） |
| 门禁 | 表单必填项齐；小说路径 analysis 证据校验（沿用） |

篇幅档位：S ≈ 15 分钟 / 25 张卡；**M ≈ 30 分钟 / 60 张卡（对标金样本）**；L ≈ 60 分钟 / 120 张卡。

### 6.2 ② 世界设定集（World Bible）

| 项 | 内容 |
|---|---|
| 输入 | `ProductionBrief`（+ analysis 摘要） |
| 输出 | `WorldBible { title, premise, tone, styleGuide{ do[], dont[], sampleParagraph }, locations[≤12]{id,name,role,mood}, factions[], npcs[]{id,name,want,secret}, resourceSet, clock, hooks[] }` |
| 资源怎么定 | **从内置题材模板选**（新增 `xiuxian_cultivation` 模板 = §2.4 的形状；`stat-templates` 升 v2 带 `min/max/onMin/onMax`），模型只能在模板内改名、调范围、选 4–7 个；不允许发明引擎不支持的机制 |
| 谁做 | AI 起草 → **作者确认并锁定**（锁定后后续阶段不得改） |
| 门禁 | schema；资源数 4–7，每个有来源与去处的文字说明；styleGuide.sampleParagraph ≥ 150 字且通过 §6.6 文本规则；至少 1 个时间压力 |

### 6.3 ③ 结构计划（Structure Plan）

| 项 | 内容 |
|---|---|
| 输入 | 锁定的 `WorldBible` |
| 输出 | `StructurePlan { endings[≥4+2]{id,title,conditionSketch,tone}, routes[]{id,name,endingIds,keyResources}, progression{realms[], expectedMonths[]}, clockWindows[], pool[]{cardId, type:'main'|'repeat'|'trigger', locationId, intent(≤60字), gate[], effectSketch[], repeat?, variants} }` |
| 谁做 | AI 起草卡池计划（只有意图和数值草图，**不写正文**）；**规则**检查；作者锁定 |
| 门禁（规则） | 结局 ≥ 4 + 2 且条件都只用已声明资源；每个资源 ≥ 1 来源 + ≥ 1 去处 + ≥ 3 处门控；卡池数量 ≥ 档位目标；每个地点 ≥ 3 张卡；每条路线 ≥ 6 张主线卡；**抽象模拟**（只用 effectSketch 跑 200 局）每个结局可达 |

### 6.4 ④ 内容生成（逐卡）

| 项 | 内容 |
|---|---|
| 输入 | `WorldBible`（含文风）+ `StructurePlan` 中的**一张卡**的计划 + 相邻卡的意图摘要 + 已写好的 2 张同地点卡（保持连续性）+ 金样本 2 张 few-shot |
| 输出 | `StoryletCard`（§3.2(c) 的形状：正文 / 变体 / 选项 / 条件 / 效果 / 结果文案） |
| 谁做 | **AI 一卡一调用**，可并发；规则逐卡校验 |
| 门禁（逐卡、不过就带问题回喂重写，≤ 3 次） | schema；只用已声明的资源和地点；效果与 effectSketch 的方向一致、幅度在 ±50% 内；正文 120–400 字、变体之间相似度 < 0.6；禁用句表；选项 2–4 个、至少 1 个有代价 |
| 同样逐卡 | 地点正文、结局正文、失败态正文 |

### 6.5 ⑤ 组装

规则把 Bible + Plan + 所有卡**确定性地**拼成 `WorldContent`（含 `resourceDefs` / `clock` / `storylets` / `endings`）。不调模型。

### 6.6 ⑥ lint v2（规则，作者可随时跑）

**挡不挡发布（D7）**：lint 对所有世界都跑、都报告。**error 只挡用了新系统的世界**（含 `resourceDefs` / `storylets` / `clock` 任一）；旧形状世界只报告不挡（UI 主行写「旧形状内容 · 不挡发布」），所以 §3.3 的旧测试原样通过。

| 类别 | 检查（error = 新系统世界挡发布；warning = 提示） |
|---|---|
| 结构（沿用并扩到卡池） | 开局可执行 ≥ 3（error）；结局可达（error）；无死路：任何可达状态至少 1 个可点行动或已结局（error，靠模拟器）；条件引用未声明的资源（error） |
| 资源平衡 | 资源无来源或无去处（error）；门控阈值超出 `[min,max]`（error）；某门控在 200 局模拟中从未满足（warning）；资源长期贴顶 / 贴底 > 50% 回合（warning） |
| 卡池 | 可重复卡 < 档位目标（error）；可重复卡变体 < 2（warning）；某卡从未被抽到（warning） |
| 文本（**新**） | 禁用句表命中（error，起始表：「气氛紧绷」「每个选择都有代价」「你来到「」「结局将近」「命运的齿轮」等，可在设定里扩）；正文低于最短长度（error）；两段非变体正文 5-gram Jaccard > 0.6（error）；全局高频句式（同一 12 字片段出现 > 3 次，warning）；选项标签空洞（沿用 EMPTY_LABEL） |
| 体量 | 总字数、卡数、结局数低于档位目标（error） |

### 6.7 ⑦ 模拟试玩报告（规则）

- 无头跑 `packages/play-runtime`（与玩家包同一引擎），策略：`random`、`greedy-修为`、`greedy-灵石`、`魔道`（心魔相关选项优先）、`偷懒`（只修炼）；每种 200 个种子。
- 报告：每个结局的到达率（按策略）；首通决策数 / 读到的不重复字数中位数；资源曲线（P10/P50/P90）；卡被抽中率与从未出现的卡；死路数；连续重复率；锁定选项比例。
- 输出 `PlaytestReport` JSON + 工作台里一页可读报告；同一份报告就是 §1 及格线 G1–G8 的自动判定。
- **S1 里模拟报告只报告、不挡发布**；S3 起按 §8 的档位阈值接入发布门禁。

## 7. 作者侧真模型接入（设计）

> 只用于作者侧生成。玩家侧（导出包）仍然 `ai.mode:'none'`，真 AI 入局属 M4。
>
> **已定（Q3 = A）**：沿用现有模型配置（`.env` / 「模型设置」里的 OpenAI 兼容中转）；每局 token 上限 **60 万**；S2 验收时用同一段想法对比两家模型，再定默认。密钥由用户在「模型设置」里填，策划与 Coder 不经手。

### 7.1 Provider 抽象

- 沿用 `ChatCompletionsProvider`（OpenAI 兼容），新增一层 **`StageModelRouter`**：按阶段选模型。
  - `bible` / `structure`：强模型（长上下文、结构推理好）。
  - `card` / `rewrite`：快模型（便宜、并发高；中文文笔优先）。
  - 未单独配置时全部回落到「模型设置」里的默认模型。
- 结构化输出：优先 `response_format: { type: 'json_schema', schema }`（schema 由 zod `toJSONSchema` 生成）；服务端不支持时回落 `json_object` + 本地 zod 校验（今天的做法）。
- 校验失败：把 zod 问题 + 规则问题（禁用句命中、超出范围……）整理成 `ModelRepairFeedback` 回喂，**同一卡最多 3 次**；仍失败则该卡标「生成失败」，不阻塞其它卡，作者可单卡重试。
- 网络 / 429 / 5xx：沿用 `retry.ts` 指数退避 + `Retry-After`。
- 密钥只在服务器；日志不记 prompt 全文与密钥（沿用）。
- **mock 只留给测试**：`mock-llm.mjs` 继续服务管线 e2e；生成的草稿打上 `generator:'mock'`，非测试环境禁止发布（§6.9）。

### 7.2 阶段与 prompt 计划

| 阶段 | 调用次数（M 档） | 系统提示要点 | 输出 schema |
|---|---|---|---|
| bible | 1 | 题材模板内选资源；必须写 sampleParagraph；禁止发明机制；禁用句表 | `WorldBible` |
| structure | 1–2（卡池 > 40 时按地点分两次） | 每个资源 ≥ 3 处门控；结局条件只用已声明资源；卡只写意图不写正文 | `StructurePlan` |
| card | ≈ 60 卡 + 9 地点 + 8 结局 ≈ **77** | 文风指南 + 金样本 few-shot 2 张 + 该卡计划 + 邻卡摘要；正文 120–400 字；变体互不相似 | `StoryletCard` / `LocationText` / `EndingText` |
| rewrite | 按需 | 原卡 + 作者意见 + lint 问题；不得改 id、条件阈值（除非作者解锁） | `StoryletCard` |

### K15 结局附加段落与「这一生」回顾（2026-10-28 补，策划定）
- `endings[].passages[]`：每条 `{id, when: Condition, text}`，结局正文之后按数组顺序追加所有 `when` 成立的段落；条件求值用结局触发时的状态，结果写入存档的结局快照，读档不重算。
- 顶层 `recap[]`：每条 `{id, when: Condition, text, order?}`，结局页底部「这一生」区块按 order（缺省为数组序）列出成立的条目；无成立条目时整块不显示。
- `endings[].textVariants`：沿用剧情卡 textVariants 的写法，条件成立时整段替换结局正文（先替换，再追加 passages）。
- `when` 与剧情卡条件同一写法：数组表示全部成立，可嵌套一层 `kind:"anyOf"`；也接受单个条件对象。
- 筛选和排序都在 play-runtime 里完成，结局页只拿到已成立、已排好序的列表；recap 默认按数组顺序，有 order 时按 order 稳定排序，作者需保证有先后依赖的条目相邻。
- recap 全部列出，不截断。
- 只用现有 Condition 语法，不新增条件种类；lint 需检查：id 唯一、text 非空、条件引用存在、每个结局至少 1 条 recap 可达（warning）。
- 玩家端不显示未成立的段落/条目（防剧透）；包体仍受 §9 预算约束。
- 结局页的版式由 UI 出小规划确认后再做；引擎/导入/lint/存档部分可先做。
