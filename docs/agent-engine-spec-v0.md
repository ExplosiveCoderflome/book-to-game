# 智能体游戏环境：规范层与积木库设计（v0 草案）

> 状态：2026-11-05 群里用户点头「先搞出来一版再细化」。策划出，交 Coder 评估可落地性并拆任务。未 commit。
> 承接：`engine-vision-plan.md`（BlockSpec / 爽感画像）、`extensibility.md`（五层分离、KindRegistry）。本文把它们收成「给智能体用的环境」的正式规范；冲突处以本文为准，待用户确认后回写。

## 0. 一句话

产品从「小说转游戏的固定管线」改为**引擎之上的一层环境**：我们只提供**规范**和**积木库**，由智能体按规范挑积木、配参数、写内容，必要时在沙箱写扩展；规范和检查保证拼出来的游戏一定能跑、能存档、能离线打包。

## 1. 四层与职责

| 层 | 内容 | 谁写 | 不允许 |
|---|---|---|---|
| 引擎 | `play-runtime`：状态、命令、存档、种子随机、模拟 | Coder | 出现任何题材分支 |
| 规范层 | 世界文件格式、积木声明格式、扩展契约、检查清单、版本规则 | 策划定，Coder 落 schema | 写死题材词汇 |
| 积木库 | 按玩法分类的可复用积木（K1–K16 迁入） | Coder 实现，策划定参数与验收；作者可扩充 | 积木自建并行状态机（必须 compile-down 到引擎状态） |
| 智能体层 | 读规范 → 选积木 → 配置 → 写内容 → 体检 → 修 | AI | 直接写引擎状态；绕过检查进包 |

## 2. 规范层

### 2.1 一个世界由什么组成（World Package）

```
world/
  manifest.json      # id、标题、spec 版本、引用的积木及版本、爽感画像、打包目标
  state.json         # 数值/资源/旗标定义（含上下限、显示名）——唯一状态真相
  blocks/*.json      # 每个积木实例的参数配置
  content/           # 剧情卡、地点、结局、回顾、文案（纯数据）
  ext/*.js + *.ext.json   # 智能体扩展（可选，见 §4）
  checks.json        # 本作的验收阈值（由画像生成，可微调）
```

规则：所有状态必须在 `state.json` 声明；积木与扩展只能引用已声明的状态。

### 2.2 积木声明（BlockSpec）必填项

| 字段 | 说明 |
|---|---|
| `id` / `version` | 破坏性变更升主版本，禁止静默改名 |
| `category` | §3 的分类之一 |
| `reads` / `writes` | 读写的状态类别或具体键；写须给**单次改动上限** |
| `params` | 参数、类型、默认值、合法范围 |
| `hooks` | 触发时机，闭集：`onStart` `onTurn` `onTimeAdvance` `onAction` `onEnter` `onEnding` `onLoad`(只读) |
| `requires` / `conflicts` | 依赖哪些积木、与哪些互斥 |
| `provides` | 编译产物落到 WorldContent 的哪个片段 |
| `checks` | 自带的 lint 规则与模拟指标 |
| `playerUi` | 需要哪个玩家端组件（无则空），新组件须走 UI 流程 |
| `funTags` | 提供的体验标签（沿用 vision §2.1 闭集） |

### 2.3 条件与效果的统一语法

沿用 K15 已定写法：条件为数组（全成立）/ 单对象 / 一层 `anyOf`；比较 `atLeast` `atMost` `eq` `has`。效果为 `add` `set` `grant` `revoke` `advanceTime`，每条都受目标状态上下限钳制。积木和扩展都只能产出这两种东西。

### 2.4 检查（发布门槛）

1. **结构**：schema 校验、引用完整、未声明状态零引用。
2. **积木**：依赖与互斥满足、参数在范围内、版本兼容。
3. **内容**：无 mock/模板句、文案长度与重复率（沿用 S1 lint）。
4. **模拟**：按画像跑 N 个种子（默认 2000）× 策略集，查死局、卡死、越界、结局分布、时长（G1–G10 按画像解析阈值）。
5. **扩展**：§4.4。
6. **打包回归**：单文件 HTML、exe、手机 390×844、离线到结局、存档读回一致。

任何一项 error 不得发布；warning 进报告由作者决定。

### 2.5 版本规则

- `spec` 版本写在 manifest；引擎声明支持区间，旧世界自动迁移或拒绝加载并说明原因。
- 积木小版本只能加可选参数；改语义升主版本，旧主版本保留至少一个大版本周期。
- 存档记录 spec 与各积木版本；读档不重算已快照的结果（K15 纪律）。

## 3. 积木库分类（按玩法职能）

| 分类 | 管什么 | 现有（迁入） | 第一批要补 |
|---|---|---|---|
| 状态与资源 `stat` | 数值、资源、上下限、显示 | 数值模板、资源当条件 K* | 资源模板去仙侠默认词 |
| 时间 `time` | 时钟、期限、时段 | 月时钟 | 日/周/年单位、营业日 |
| 剧情 `story` | 剧情卡、事件池、手牌、按状态文案 | storylet、textCases、可重复卡 | 连锁事件、冷却 |
| 角色与开局 `actor` | 出身、天赋、开局随机、NPC | K16 openingRoll | NPC 关系、日程 |
| 空间 `space` | 地点、地图、旅行、填充 | 世界地图、map.fill | 旅行耗时、区域解锁 |
| 物品与建筑 `economy` | 物品、商店、建筑、产出 | 物品库、建筑库 | 经营循环、价格波动 |
| 冲突 `conflict` | 遭遇、检定、战斗 | 遭遇桩 | 检定积木（属性+骰） |
| 结局与回顾 `ending` | 结局判定、附加段落、这一生 | K15 | 多周目继承（后置） |
| 呈现 `present` | 玩家端组件绑定 | 结局页、开局页 | 仅登记，不让智能体自造 UI |
| AI 接入 `ai` | 运行时旁白/建议/NPC 对话的插口 | manifest 预留位 | 受约束输出（只出文本或已声明效果） |

每个积木在库里附：一句话用途、最小示例、适用画像、已知坑。

## 4. 智能体扩展契约

### 4.1 分级（能不写代码就不写）

1. 现成积木配参数；
2. 受限规则表达式（§2.3 语法 + 算术，不图灵完备）；
3. 沙箱脚本（最后手段）。智能体必须在扩展声明里写明为何 1、2 不够，检查器会抽查。

### 4.2 扩展点（闭集）

`condition`（返回真假）、`effect`（返回效果列表）、`eventGen`（从池中选卡/生成卡参数）、`rollRule`（随机分布）、`endingJudge`（选结局）、`textPick`（按状态挑文案变体）。扩展不能改引擎流程、不能新增命令、不能新增 UI。

### 4.3 声明（`*.ext.json`）

`id` `version` `point` `reads[]` `writes[]`（含单次上限）`hooks[]` `params` `reason` `tests[]`（至少 3 个输入→期望输出用例）。

### 4.4 运行与检查

- 纯函数、确定性；随机只用引擎传入的种子流；无网络、文件、时间、UI。
- 引擎只传入声明过的状态；返回值按声明和上限校验后才写回，越权整条丢弃并记 error。
- 每次执行限步数、限内存；代码大小上限。（实现建议 QuickJS-wasm，由 Coder 定。）
- 进包前：静态检查 API 白名单 → 自带用例 → 模拟 N 种子无崩溃/卡死/越界 → 与不含该扩展的基线对比，结局分布不得出现单一结局 >40%（画像可改）。
- 不过则返回结构化报错给智能体重写，最多 3 轮后交人。

## 5. 智能体工作流（默认）

画像 → 选积木（写进 manifest 并说明理由）→ 配参数 → 写内容 → 体检 → 修 → 人审 → 打包。每一步产物都是文件，可人工改、可回滚。

## 6. 第一版范围（建议）

- In：规范 schema（manifest/state/BlockSpec/ext 声明）、K1–K16 迁成积木并补声明、检查器串成 §2.4、扩展沙箱跑通 `condition`/`effect` 两个点、用《寿灯》做回归（只迁移格式不改内容）。
- Out：其余扩展点、多周目、运行时 AI、新玩家端组件、新题材金样本。

## 9. 定稿（2026-11-10，供 Coder 实现）

### 9.1 世界包结构（定稿）

- 编辑态用分文件结构（§2.1 的目录）；导出/发布时由编译器合并为单份 WorldContent JSON + manifest（含各文件 hash、spec 版本、积木版本），引擎与播放器仍只读单份 JSON，不改运行时。
- 必须文件：`manifest.json`、`state.json`、`content/`（至少一个文件）。可选：`blocks/`、`ext/`、`checks.json`。
- 拆分规则：`content/` 按类型分文件——`storylets*.json`、`locations*.json`、`endings.json`、`recap.json`、`texts*.json`；同类可拆多个，合并时按文件名排序拼接，id 冲突为 error。
- 旧世界（单份 JSON）可直接导入，导入时自动拆成上述结构；拆→合必须逐字节等价（回归条：《寿灯》只读样例拆合后与原文件规范化后一致）。

### 9.2 扩展测试用例（定稿）

- 每个扩展 `tests[]` 至少 3 条，少于 3 条为 error，不得进包。
- 3 条中至少 1 条为边界用例（状态取上限或下限），`effect` 类至少 1 条期望输出为空或不改动。
- 用例全部执行且全过才进入模拟检查；任一不过记 error 并打回，打回计入「最多三轮」。

## 10. 第 8 项验收条（2026-11-10 群内定）

1. 一句点子 → 浏览器全程操作 → 可试玩，中间无人工改文件。
2. 正文无 mock/模板句，全部检查无 error。
3. ≥2 个可达结局；2000 种子模拟无死局，最高结局占比 ≤40%。
4. 单局时长 ≥15 分钟（中位步数 ×（正文字数/400 字每分钟 + 10 秒选择））。
5. 导出单文件 HTML，375×812 视口离线打开可玩到结局。

2–4 做成自动检查回馈 Agent 自修；成品先交策划亲玩再判。Windows 播放器/exe 兼容暂停，只保证现有导出代码不被改坏。
