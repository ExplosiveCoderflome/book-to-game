## 1. 产品愿景与单局成功

### 1.1 一句话愿景

> 把小说改编成**可玩的文字游戏**：同一套硬状态基底上，作者可做「分支故事」或「开放冒险」；玩家每一步都**看得见选择、付得出代价、感受得到世界回应**，而不是翻页或走廊。

### 1.2 单局成功定义（跨模式）

一局「算成功」当且仅当玩家在有限步数内：

1. **开局就能动**：起始至少有 ≥2 个去向不同的有意义行动（对照 rubric D1）；  
2. **行动有反馈**：文案变化 +（尽可能）数值/资源/事实 delta 可见（对照 D2、D6）；  
3. **路径分得开**：不是单脊走廊或立刻汇合的假分支（对照 D4）；  
4. **到达可感结局**：至少两条结局在语气/代价/世界状态上可区分，或明确的失败态（对照 D3、D9）；  
5. **规则诚实**：UI 显示可点的行动，真的可执行；锁定有可读原因（开放对照 D7）。

**小说忠实度**是加分项，不是单局合格的前置条件。原著对不上但可玩，优先于原著对得上但不可玩。

### 1.3 双模式 · 一套 Substrate

| 模式 | 内容模型 | 运行时模块 | 玩家主要动词 |
|---|---|---|---|
| **分支故事（story）** | 场景图 + 选项边 + variables | `sessions` | 读场景 → 选选项 |
| **开放冒险（open）** | 地点 / 行动 / 事实 / 人物知识 / 地图填充 | `adventure-sessions` | 看地点 → 行动或移动 |

两套内容模型刻意分治，但共享：

- `variables` / conditions / effects（经 **KindRegistry**）  
- 世界书硬约束（forbid / gate / cap / spend…）  
- Catalog compile-down（数值模板、地图模板、建筑库、物品目录）  
- AI **不得**在规则引擎外改写 session  

**禁止**按题材（修仙 / 都市 / 废土）分叉 runner；题材只填 **形状模板**（stat templates、map templates、building/item Catalog）。

### 1.4 推进线路与多路径（主脊 + N 条有效岔路）

文字游戏需要**推进感**，但不等于必须做成「一条主线任务列表 + 旁边挂支线」。合格形状是：

| 概念 | 含义 | 合格要求 |
|---|---|---|
| **总目标（推进脊）** | 本局要弄清什么 / 活过什么 / 站哪边 | 玩家开局能说出「我在追什么」；对照 §5.1 Goal shapes |
| **主路径** | 最容易读到的一条推进链（可是作者推荐序，不是唯一合法序） | 有清晰节拍；**不是**强迫玩家只能走这一条 |
| **N 条有效分支** | 不同选择接到不同中间局面，并影响结局/代价/信息 | 分支须改资源、关系、事实或结局；禁止换皮假分支（对照 D2、D4） |
| **可感结局** | ≥2 条终局在语气 / 代价 / 世界状态上可区分 | 对照 D3、D9 |

**按模式怎么落地：**

| 模式 | 推进脊长什么样 | 分支长什么样 |
|---|---|---|
| **分支故事（story）** | 场景图上的推荐序 / 关键旗推进（信息、关系、结局旗） | **显式选择边**分叉；拉开结局靠中途状态 + 结局文案，不靠隐形连线 |
| **开放冒险（open）** | 主目标形状（survive / investigate / explore…）+ 地点目标提示 | **地图上多条腿走路**：不同地点策略、任务/遭遇取舍、资源路径；不是旁支任务栏装饰 |

**纪律（与 §2 灵活图一致）：**

- 要有「往前推」的感觉 + 多条真岔路；  
- **不要**强制「主线 1→2→3，支线挂旁边」才算有结构；  
- 节点/地点之间**只有显式边或显式行动**才算关联；假双结局、立刻汇合的假分支 = 不合格。

### 1.5 玩法口味模板（体感区分 · 禁止分叉 runtime）

玩家体感上可以、也应该区分不同「玩法口味」——但 **book-to-game 用 Catalog / 题材包模板切换口味，不做成多套互不相通的引擎**。

| 口味 id（示意） | 玩家主要爽点 | 推进脊偏重 | 默认启用深度 | 说明 |
|---|---|---|---|---|
| `plot`（剧情推进） | 选择、人物、结局差异 | investigate / relation / resolve | **P0 核心** | 经典分支故事与偏叙事的开放局 |
| `growth`（成长数值） | 变强、配装、养成可见 | survive + 资源/能力旗成长 | **轻量即可** | 用 variables / resources / 能力旗表达「变强」；**完整升级打怪 RPG 非目标** |
| `explore`（探索经营） | 跑图、交易、据点互动 | explore / deliver + 填充建筑 | **P1 切片** | 迷雾、商店/补给/任务桩服务开放循环 |
| `combat`（遭遇冲突） | 风险选择、遭遇后果 | encounter / boss 桩 + 掉落反馈 | **P2 加深** | 触发与反馈即可；**禁止**冒充完整战斗仿真已完成 |
| `idle`（放置挂机） | 离线涨数 | — | **非目标** | 不进入默认循环；不为此加 runner |

**与双模式的关系：**

- `story` / `open` 是**内容模型 + 运行时模块**（§1.3）；  
- `plot` / `growth` / `explore` / `combat` 是**体感口味**，叠在任一模式上，靠数值模板、地图模板、建筑/物品 Catalog、目标形状组合出来；  
- 同一局可以「主口味 + 辅口味」（例如 explore 为主、plot 为脊），但 **HUD / 选项 / delta 仍走同一套 Perceive→Decide→Act→Feedback**。

**产品优先级（与 §8 分期对齐）：**

1. 先保证合格文字游戏：有意义选择 + 世界会回应 + 推进脊清晰；  
2. 开放优先 **explore + 轻互动桩**，剧情向用 **plot**；  
3. **growth / combat** 只做可见轻量反馈，完整打怪升级与放置后置或永不做。

## 2. 双模式共用的核心闭环

文字游戏的「心跳」不因模式而变。任何一拍都应能回答：**我看见了什么 → 我选了什么 → 世界怎么变了 → 下一步还能做什么**。

```text
  ┌─────────────────────────────────────────────────────────────┐
  │                     PLAYER LOOP（共用形状）                    │
  │                                                             │
  │   Perceive          Decide           Act           Feedback │
  │  ┌─────────┐     ┌─────────┐     ┌─────────┐     ┌────────┐ │
  │  │ HUD     │     │ 权衡选项 │     │ 经规则  │     │ 文案   │ │
  │  │ 地点/场景│ ──► │ 代价可见 │ ──► │ 引擎    │ ──► │ +delta │ │
  │  │ 选项列表 │     │ 条件诚实 │     │ KindReg │     │ 新选项 │ │
  │  └─────────┘     └─────────┘     └─────────┘     └────┬───┘ │
  │       ▲                                               │     │
  │       │         Progress / Fail / Ending              │     │
  │       └──────────── 未终局则回到 Perceive ◄────────────┘     │
  └─────────────────────────────────────────────────────────────┘
```

| 节拍 | 玩家感受到什么 | 系统必须提供 |
|---|---|---|
| **Perceive（感知）** | 我在哪、我有什么、我能做什么 | 场景/地点文案；HUD（variables / resources）；过滤后的选项/行动；锁定项的原因（若有） |
| **Decide（决策）** | 选项之间有冲突与代价，不是「继续 A / 继续 B」 | 标签可读；代价/花费提示；世界书 cap 预告（若适用） |
| **Act（行动）** | 点下去真的发生了 | 只经 sessions / adventure-sessions 端口；conditions 求值 → effects 应用；**AI 旁白/提案不得提交状态** |
| **Feedback（反馈）** | 世界回应了我 | 结果文案；**数值 delta**；新解锁/消失的选项；事实与人物知识更新（开放） |
| **Progress / Fail / Ending** | 我在靠近目标，或明确失败/通关 | 结局节点 / 开放结局条件；失败态有反馈而非无声超时 |

**灵活图纪律**（与 playtest-rubric 一致）：节点之间**只有显式边**才算关联；不要过度锁死「剧情必然」。拉开结局差异靠改结局文案与中途状态，不靠隐形连线。

## 3. 分支故事循环（story）

### 3.1 循环形状

```text
场景文案 + HUD
    → 条件过滤后的选项列表（不可见 / 可见不可点须诚实）
    → 玩家选择
    → 应用 effects（经 KindRegistry）+ 世界书 spend/cap
    → 旁白（可选，prompt-only，不改状态）
    → 下一场景 或 结局节点
```

与**无限画布**的关系：

- 作者主路径 = 在画布上增删改**场景节点**与**显式选择边**；  
- 可玩性门禁约束的是出度、分叉、效果覆盖、结局体感——**不是**强迫节点两两耦合；  
- 变量初值、选项 conditions/effects 在检查器编辑；玩时投影与权威求值共用 `@novel-game/rules`。

### 3.2 合格标准钩子（对照 rubric，摘要不替代原文）

| 闭环节拍 | 主要对照 | 作者自检一句话 |
|---|---|---|
| Perceive 开局 | **D1** 开局密度 | 起始 ≥2 不同目标的有意义选项？ |
| Decide | **D2** 有意义分支代价 | 关键选择是否改变资源/关系/信息？ |
| Act → Feedback | **D6** 状态后果可见 | 变量是否驱动解锁或改写后续？ |
| 路径结构 | **D4** 反走廊 | 是否存在通向不同结局的独立路线？ |
| 节奏 | **D5** 会话长度 | 最短不过短；前 2–3 步有可见变化？ |
| 终局 | **D3** 结局可感差异 | ≥2 结局在语气/代价/世界状态上可区分？ |
| 再玩 | **D9** | 打完是否想换一条路？ |

门禁级错误（开局 0 选项、走廊 error、假双结局等）→ 单局不合格，优先改图与效果，而不是只改文案。

### 3.3 故事模式特有的「成长」载体

| 载体 | 形状 | 可见反馈要求 |
|---|---|---|
| 信息 | 后续场景文案变化 / 解锁选项 | 玩家能复述「因为我知道了 X」 |
| 关系 / 信任 | variables（数值或布尔） | HUD delta 或选项标签体现 |
| 资源 / 体力 | variables 或 resources（若故事侧启用） | 花费前提示，结算后 delta |
| 能力旗 | boolean variables / facts | 解锁新选项，而非隐藏改表 |

## 4. 开放冒险循环（open）

### 4.1 循环形状

```text
当前地点文案 + 迷雾/已知区域 + HUD（resources / variables）
    → 建议行动 ∪ 移动目标（availableWhen / requires 诚实过滤）
    → 玩家行动或移动（耗时 / 花费 / 风险提示）
    → 规则引擎：改 resources、facts、人物知识、时间事件
    → （可选）地图填充互动桩：商店买 / 补给 / 任务槽 / 遭遇
    → 旁白或天道修正（prompt-only）
    → 检查目标 / 失败 / 结局；否则回到地点感知
```

### 4.2 与地图填充、建筑、物品的关系

开放循环的**主干**仍是：地点 → 行动/移动 → 状态 → 目标。

[`items-and-building-content.md`](./items-and-building-content.md) 与 [`world-map-editor.md`](./world-map-editor.md) §9 提供的是**可复用互动形状**，用来丰富开放循环，而不是另起一套游戏：

| 建筑 kind | 玩家循环中的位置 | 玩时真相（compile-down） |
|---|---|---|
| shop | Decide/Act：买/看货 | 扣本世界 `resourceId` + 获得 item/fact 桩 |
| supply | Act：恢复 | 改 variables / resources（世界绑定目标） |
| quest | Perceive/Progress：接/交任务 | 任务旗 facts；交付引用 Item Catalog |
| encounter / boss | Act：触发遭遇 | `start_encounter` 桩 + 掉落表；**完整战斗仿真非目标** |

Catalog 只提供形状与偏好；**真价、真 resourceId、真任务旗在世界绑定 / 地图放置时生成**（见 items §6）。

### 4.3 迷雾与探索

- **Perceive**：只展示已知/可见区域与可执行行动；迷雾外不可点、不剧透。  
- **Progress**：探索本身可以是目标类型之一（揭开区域、到达地标）。  
- 合格对照：**D1**（开局可执行密度）、**D7**（条件诚实）、**D5**（非只能空等到超时）。

### 4.4 开放模式合格钩子（摘要）

| 闭环节拍 | 主要对照 | 自检 |
|---|---|---|
| 开局可动 | D1、D7 | 初始可执行 ≥2，且不只是等待；可见≈可点 |
| 策略 | D8（人工） | 至少两条可感不同的主策略（非永远同一套路） |
| 状态 | D2、D6 | 行动留下资源/信任/暴露等后果，且可见 |
| 终局 | D3、D5、D9 | 存在非超时结局；失败有反馈；愿再开一局 |

## 5. 单局目标 / 失败 / 成长（跨模式）

目标、失败、成长都描述为**可模板化的形状**，由题材包 / 数值模板 / 地图模板填具体名词——**禁止**在循环文档或 runner 里写死「修仙渡劫 / 都市查案」数值。推进脊与多路径见 **§1.4**；玩法口味（剧情 / 成长 / 探索等）见 **§1.5**——口味只改模板组合，不改本节形状闭集。

### 5.1 目标类型（Goal shapes）

| 形状 id（示意） | 玩家体感 | 典型结束条件形状 | 谁填具体内容 |
|---|---|---|---|
| `survive` | 活过时限 / 撑过压力 | 时间到且关键资源 ≥ 阈；或压力变量未爆 | 数值模板 + 世界时限 |
| `investigate` | 查清真相 | 关键 facts 集合满足；或到达结局旗 | 世界书 / 事实编目 |
| `relation` | 关系达成或挽回 | 关系变量 gte / 特定选项路径 | 变量模板 |
| `escort` / `deliver` | 护送到点 / 交货 | 地点到达 + 物品 fact 仍在 | 地图 + Item Catalog |
| `explore` | 揭开区域 / 拜访地标 | 迷雾揭开计数 / 区域 flags | 地图模板 |
| `resolve` | 多结局中的「选定结局」 | 到达 tagged ending | 画布结局节点 |

作者可选一个主目标 + 若干软目标；UI 应用**目标提示**，不要把目标写成不可见的隐藏计数器。

### 5.2 失败形状（Fail shapes）

| 形状 | 体感 | 反馈要求 |
|---|---|---|
| 死路 / 无行动 | 卡死 | 明示原因；避免「只能空等」无文案（开放 D5/D7） |
| 资源耗尽 | 钱/粮/体力归零且关键行动全锁 | HUD 先预警；失败结局或明确失败态 |
| 时限到期 | 时钟走完未达成 | 超时结局文案，区分「差一点」与「彻底失败」若可行 |
| 关系崩坏 | 信任/声望跌破 | 选项消失或转向敌对线；delta 可见 |
| 被发现 / 暴露 | 身份或阴谋暴露 | 触发遭遇或坏结局；不要静默改表 |
| 条件锁死假结局 | 表面双结局实际不可达 | 发布门禁拦截（D3） |

### 5.3 成长形状（Growth shapes）

成长 = **玩家能说出自己变强/变富/变知情的那一句话**，对应可见反馈：

| 成长维 | Substrate 载体 | 可见反馈（硬要求） |
|---|---|---|
| 信息 | facts / 人物知识 / 场景文案 | 新线索列表、解锁选项标签 |
| 资源 | `resources` / 堆叠材料 | HUD 数字 + 购买/花费 delta |
| 关系 | variables | HUD 条/数 + 选项开闭 |
| 能力旗 | boolean variables / item facts | 「已学会/已获得」标记；新行动出现 |
| 空间 | 迷雾 / 已知地点 | 地图揭开动画或列表增量 |

**禁止**把成长做成纯后台改表、HUD 无变化、选项无开闭——那会直接打穿 D2/D6。

## 6. 系统咬合表

| 系统 | 在闭环中的职责 | 可做 | 禁止 |
|---|---|---|---|
| **选择（story choices / open actions）** | Decide + Act 的主入口 | 条件过滤、效果应用、代价文案 | 无状态的「继续/随便看看」占主导 |
| **移动（open）** | 空间感知与探索 Progress | 耗时、区域条件、迷雾更新 | 无代价瞬移掩盖资源循环（设计上可有，但须诚实提示） |
| **数值 / resources** | Perceive HUD + Feedback delta | 模板 compile-down；花费与恢复 | 题材专属 runner；库资产写死某世界 `resourceId` |
| **世界书硬约束** | Decide 预告 + Act 强制 | forbid / gate / cap / spend | AI 或 UI 绕过约束改状态 |
| **地图填充建筑** | 开放循环的互动富化 | 引用 Item Catalog 的硬行；放置 overrides | 建筑自造自由文本物资当玩法真值；完整经济/战斗仿真冒充已完成 |
| **物品目录** | 跨建筑复用的物品身份 | 类别闭集、提示价、硬引用删除保护 | 平行背包 runtime |
| **AI · 作者时** | 生成骨架、提案物品/货架/填充 | 草稿 → 人审 → 写入 Catalog/草稿 | 无人审直接当已发布真值 |
| **AI · 玩时** | 旁白、propose-act、**天道修正** | **prompt-only** 映射到已有行动/文案 | **mutate session**；发明规则引擎没有的 effect |

一句话纪律（与 extensibility 对齐）：

> **状态真相在 Substrate；循环形状在本文；题材名词在 Catalog；智能只建议不提交。**

## 7. 作者生产流水线如何服务这个循环

```text
小说语料
  → 结构草稿（场景图 或 地点/行动世界）
  → 人审 / 地图确认锁（开放）
  → Catalog 填充（数值模板 · 物品 · 建筑 · 地图填充）
  → 试玩（对照 playtest-rubric）
  → 发布固定版本
```

| 流水线阶段 | 服务哪个闭环节拍 | 验收钩子 |
|---|---|---|
| 选章与身份 | 开局 Perceive 的立场 | 开局是否立刻有冲突焦点 |
| 生成/手改结构 | Decide 的选项密度与分叉 | D1、D4 自动信号 |
| 变量/效果/世界书 | Act + Feedback | D2、D6；effects 占比软门禁 |
| 地图确认 → 填充 | 开放 Perceive/互动 | 未确认拒绝放置；填充 kind 闭集 |
| 物品/建筑 Catalog | 开放 Act 富化 | 硬行引用 itemId；空模板合法 |
| 试玩 HUD/代价/delta | Feedback 体感 | 人工 D2/D6/D9；截图可展示 delta |
| 发布门禁 | 整局合格 | 单篇维度 ≥3；D1/D3/D4 硬门槛 |

**作者时延申（L3）**与**玩时天道**都不得破坏：试玩可复现、发布可审计、存档可回放。

## 8. 分期建议（玩法向 · 非实现强制）

| 期 | 目标 | 玩家循环收益 | 明确非目标 |
|---|---|---|---|
| **P0** | 把**现有试玩反馈做满** | HUD 完整、选项代价可见、结算 **delta**、结局文案可感差异；故事与开放都对照 D1–D6/D9 拉到 ≥3 | 新玩法系统；自由文本行动；完整数值 RPG |
| **P1** | **开放世界填充可玩切片** | 在已确认地图上：商店购买桩、补给恢复、任务点接取桩可走通一圈 Perceive→Act→Feedback | 完整商店仿真、拍卖、制作树；完整任务图引擎 |
| **P2** | **更深遭遇 / 任务** | 遭遇触发 + 掉落反馈；任务交付/奖励闭环可复述；多策略可感（D8） | 实时战斗、装备槽 RPG、冒险经历→小说回写 |
| 更后 | 题材包默认内容、目标/失败模板库、作者向「循环体检」面板 | 降低空白世界的空转感 | 按题材分叉 runtime |

**全局非目标（本文锁定，与 README / items / §9.10 一致）：**

- 自由文本行动（parser IF）作为主循环  
- 完整数值 RPG（装备槽、技能树、回合制战斗仿真）  
- **放置 / 挂机（idle）作为默认循环**（§1.5）  
- 按玩法口味或题材 **分叉 runner**（口味只用 Catalog / 模板）  
- 冒险经历自动改写成小说  
- AI 在规则引擎外改写存档  
- Catalog 库资产绑死某一世界的货币名 / 任务旗 / 气血变量名
